Guía paso a paso para llevar el dashboard y sus microfrontends a producción en una instancia Ubuntu de AWS EC2, con dominio propio, HTTPS y capacidad de escala.

🗺
Arquitectura de producción
Cómo se conectan todas las piezas en el servidor
En desarrollo usas múltiples terminales y puertos distintos. En producción todo el tráfico entra por un solo punto (Nginx en el puerto 443/HTTPS) y se distribuye internamente a cada contenedor Docker. El usuario final solo ve tu dominio — nunca los puertos internos.
Internet
│
Nginx (puerto 443 HTTPS / 80 HTTP) ← único punto de entrada
├── tudominio.com/* ──▶ Host container :3000 (Next.js — dashboard)
├── mfe-tx.tudominio.com/* ──▶ MFE transactions :3001
└── mfe-users.tudominio.com/* ──▶ MFE users :3002
Red Docker interna (los containers se comunican entre sí)
Host ─────────────────▶ MongoDB Atlas (base de datos en la nube)
🐳 ¿Por qué Docker?
Garantiza que la app funcione igual en tu máquina y en el servidor. Cada MFE vive en su propio contenedor aislado — un error en uno no afecta a los demás. Escalar es tan simple como decir "quiero 3 copias de este contenedor".
📡 ¿Por qué subdominios por MFE?
Los iframes del host necesitan una URL pública para cargar los MFEs. Usando subdominios (mfe-tx.tudominio.com) cada MFE tiene su propia dirección, Nginx lo enruta al container correcto y el certificado SSL los cubre a todos con un wildcard.
⚠️ Acción requerida antes de desplegar: los iframes del host tienen src="http://localhost:3001" hardcodeado. En producción deben leer la URL desde una variable de entorno. El Paso 1 de esta guía cubre ese ajuste.
1
Ajustar el código para producción
Cambiar las URLs hardcodeadas de localhost por variables de entorno
Actualmente los iframes del host apuntan a http://localhost:3001. En producción ese URL no existe — el servidor es tudominio.com. La solución: leer la URL del MFE desde una variable de entorno que cambia según el ambiente.
1
Editar la página de Transacciones del host
Cambiar el src del iframe para leer desde una variable de entorno.
app/dashboard/transactions/page.tsx// Antes (hardcodeado — solo funciona en local):
// src="http://localhost:3001/dashboard/transactions"

// Después (lee el entorno):
const MFE_TX = process.env.NEXT_PUBLIC_TRANSACTIONS_MFE_URL
              ?? "http://localhost:3001";  ← fallback para desarrollo

export default function TransactionsPage() {
  return (
    <iframe
      src={`${MFE_TX}/dashboard/transactions`}
      title="Módulo de Transacciones"
      style={{ width:"100%", height:"calc(100vh - 64px)", border:"none", display:"block" }}
    />
  );
}
2
Hacer lo mismo para cada página con iframe (ej: Usuarios)
app/dashboard/users/page.tsxconst MFE_USERS = process.env.NEXT_PUBLIC_USERS_MFE_URL
                ?? "http://localhost:3002";

export default function UsersPage() {
  return (
    <iframe
      src={`${MFE_USERS}/dashboard/users`}
      title="Módulo de Usuarios"
      style={{ width:"100%", height:"calc(100vh - 64px)", border:"none", display:"block" }}
    />
  );
}

Crear .env.local en el host para desarrollo (no se sube a git)

2
Crear los Dockerfiles
Un Dockerfile por aplicación — le dice a Docker cómo construir cada imagen
Un Dockerfile es una receta: le dice a Docker "descarga Node, copia el código, instala las librerías y arranca la app". El resultado es una imagen que puede ejecutarse en cualquier servidor como si fuera una cápsula sellada.
1
Dockerfile del Host dashboard-nextjs/Dockerfile
dashboard-nextjs/Dockerfile# ── Etapa 1: construir la app ──────────────────────────────
FROM node:20-alpine AS builder
WORKDIR /app

# Copiar manifiestos de dependencias primero (mejor cache de Docker)
COPY package.json package-lock.json* ./
RUN npm ci

# Copiar todo el código fuente
COPY . .

# Construir Next.js para producción
# Las variables NEXT_PUBLIC_* deben estar disponibles en build time
ARG NEXT_PUBLIC_TRANSACTIONS_MFE_URL
ARG NEXT_PUBLIC_USERS_MFE_URL
RUN npm run build

# ── Etapa 2: imagen final (más liviana, sin herramientas de build) ──
FROM node:20-alpine AS runner
WORKDIR /app
ENV NODE_ENV=production

COPY --from=builder /app/.next/standalone ./
COPY --from=builder /app/.next/static ./.next/static
COPY --from=builder /app/public ./public

EXPOSE 3000
CMD ["node", "server.js"]
⚠️ Para que el Dockerfile use la etapa standalone, agrega esto a next.config.ts del host: 
const nextConfig: NextConfig = {
  output: "standalone",
};
2
Dockerfile del MFE de Transacciones transactions-mfe/Dockerfile
transactions-mfe/DockerfileFROM node:20-alpine AS builder
WORKDIR /app
COPY package.json package-lock.json* ./
RUN npm ci
COPY . .
ARG NEXT_PUBLIC_API_URL
RUN npm run build

FROM node:20-alpine AS runner
WORKDIR /app
ENV NODE_ENV=production
COPY --from=builder /app/.next/standalone ./
COPY --from=builder /app/.next/static ./.next/static
EXPOSE 3001
CMD ["node", "server.js"]

Agrega output: "standalone" también al next.config.ts del MFE.

Copia este Dockerfile para cada MFE — solo cambia el EXPOSE por el puerto correspondiente.

3
Docker Compose — orquestar todos los contenedores
Un solo archivo para arrancar el host, los MFEs y Nginx juntos
Docker Compose es como un director de orquesta: levanta todos los contenedores en el orden correcto, los conecta en una red privada y les pasa las variables de entorno. Con un solo comando (docker compose up) arranca todo el sistema.
1
Crear docker-compose.yml en la raíz del proyecto
dashboard-nextjs/docker-compose.ymlservices:

  # ── Host — dashboard principal ─────────────────────────────
  host:
    build:
      context: .
      args:
        NEXT_PUBLIC_TRANSACTIONS_MFE_URL: https://mfe-tx.tudominio.com
        NEXT_PUBLIC_USERS_MFE_URL:        https://mfe-users.tudominio.com
    environment:
      MONGODB_URI: ${MONGODB_URI}          ← viene del .env del servidor
      NODE_ENV:    production
    ports:
      - "3000:3000"
    restart: unless-stopped
    networks:
      - app-network

  # ── MFE Transacciones ─────────────────────────────────────
  mfe-transactions:
    build:
      context: ./transactions-mfe
      args:
        NEXT_PUBLIC_API_URL: https://tudominio.com
    environment:
      NODE_ENV: production
      PORT:     3001
    ports:
      - "3001:3001"
    restart: unless-stopped
    networks:
      - app-network

  # ── MFE Usuarios (si existe) ──────────────────────────────
  mfe-users:
    build:
      context: ./users-mfe
      args:
        NEXT_PUBLIC_API_URL: https://tudominio.com
    environment:
      NODE_ENV: production
      PORT:     3002
    ports:
      - "3002:3002"
    restart: unless-stopped
    networks:
      - app-network

  # ── Nginx — reverse proxy ─────────────────────────────────
  nginx:
    image: nginx:alpine
    ports:
      - "80:80"
      - "443:443"
    volumes:
      - ./nginx/nginx.conf:/etc/nginx/nginx.conf:ro
      - /etc/letsencrypt:/etc/letsencrypt:ro   ← certificados SSL
    depends_on:
      - host
      - mfe-transactions
      - mfe-users
    restart: unless-stopped
    networks:
      - app-network

networks:
  app-network:
    driver: bridge
ℹ️ Las variables como ${MONGODB_URI} se leen de un archivo .env en el servidor (no el .env.local de desarrollo). Ese archivo nunca se sube a git — se crea manualmente en el servidor.

4
Configurar Nginx
El router que dirige el tráfico al container correcto
Nginx actúa como portero: recibe todas las peticiones en el puerto 443 (HTTPS) y las reenvía al container correspondiente según el dominio. También termina el SSL — los containers internos trabajan con HTTP simple, Nginx maneja el cifrado.
1
Crear nginx/nginx.conf en la raíz del proyecto
dashboard-nextjs/nginx/nginx.confevents { worker_connections 1024; }

http {
  # Redirigir HTTP → HTTPS
  server {
    listen 80;
    server_name tudominio.com mfe-tx.tudominio.com mfe-users.tudominio.com;
    return 301 https://$host$request_uri;
  }

  # ── Host principal ─────────────────────────────────────
  server {
    listen 443 ssl;
    server_name tudominio.com;

    ssl_certificate     /etc/letsencrypt/live/tudominio.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/tudominio.com/privkey.pem;

    location / {
      proxy_pass         http://host:3000;
      proxy_http_version 1.1;
      proxy_set_header   Upgrade $http_upgrade;
      proxy_set_header   Connection 'upgrade';
      proxy_set_header   Host $host;
      proxy_cache_bypass $http_upgrade;
    }
  }

  # ── MFE Transacciones ──────────────────────────────────
  server {
    listen 443 ssl;
    server_name mfe-tx.tudominio.com;

    ssl_certificate     /etc/letsencrypt/live/tudominio.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/tudominio.com/privkey.pem;

    # Permitir que el host incruste este MFE en un iframe
    add_header Content-Security-Policy "frame-ancestors https://tudominio.com";

    location / {
      proxy_pass         http://mfe-transactions:3001;
      proxy_http_version 1.1;
      proxy_set_header   Upgrade $http_upgrade;
      proxy_set_header   Connection 'upgrade';
      proxy_set_header   Host $host;
      proxy_cache_bypass $http_upgrade;
    }
  }

  # ── MFE Usuarios ───────────────────────────────────────
  server {
    listen 443 ssl;
    server_name mfe-users.tudominio.com;

    ssl_certificate     /etc/letsencrypt/live/tudominio.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/tudominio.com/privkey.pem;

    add_header Content-Security-Policy "frame-ancestors https://tudominio.com";

    location / {
      proxy_pass         http://mfe-users:3002;
      proxy_http_version 1.1;
      proxy_set_header   Upgrade $http_upgrade;
      proxy_set_header   Connection 'upgrade';
      proxy_set_header   Host $host;
      proxy_cache_bypass $http_upgrade;
    }
  }
}
💡 El header frame-ancestors es la versión moderna del X-Frame-Options. Le dice al navegador que solo el host (tudominio.com) puede incrustar ese MFE en un iframe. Sin esto, el iframe no carga por políticas de seguridad del navegador.

Asignar una IP Elástica (Elastic IP)
EC2 → Elastic IPs → Allocate → Associate con tu instancia. Una Elastic IP es una IP fija — sin esto la IP del servidor cambia cada vez que reinicias la instancia, lo que rompería el DNS.
✅ Anota esta IP — la usarás en el paso de DNS. Ejemplo: 54.123.45.67

Configurar el DNS
Apuntar el dominio y los subdominios a la IP del servidor EC2
El DNS (Domain Name System) traduce un nombre como tudominio.com a la IP del servidor (54.123.45.67). Necesitas crear registros de tipo A (Address) en el proveedor donde compraste el dominio.
1
Agregar los registros DNS
En tu proveedor de dominio (GoDaddy, Namecheap, Cloudflare, Route 53, etc.) busca la sección "DNS Management" o "Zone Editor" y agrega:
TipoNombre (Host)Valor (Points to)TTL
A @ (raíz) 54.123.45.67 (tu Elastic IP) 300
A mfe-tx 54.123.45.67 300
A mfe-users 54.123.45.67 300
A www 54.123.45.67 300
ℹ️ Los cambios de DNS pueden tardar entre 5 minutos y 48 horas en propagarse globalmente. Puedes verificar la propagación en dnschecker.org.
2
Si usas AWS Route 53 como proveedor de DNS
# En AWS Console → Route 53 → Hosted Zones → tu dominio
# Create Record:

Record name:  (vacío = raíz del dominio)
Record type:  A
Value:        54.123.45.67
TTL:          300

# Repetir para mfe-tx, mfe-users, www
3
Verificar que el dominio resuelve correctamente
# Desde tu terminal local (no el servidor)
nslookup tudominio.com          # debe mostrar 54.123.45.67
nslookup mfe-tx.tudominio.com   # debe mostrar 54.123.45.67

# Una vez propagado, verificar HTTPS
curl -I https://tudominio.com   # debe responder 200 OK

Actualizar el despliegue cuando hay cambios
El flujo para llevar nuevas versiones a producción
# En el servidor EC2 (conectado por SSH)
cd /home/ubuntu/dashboard-nextjs

# Traer los cambios del repositorio
git pull origin main

# Reconstruir solo el servicio que cambió (más rápido)

10
Escalabilidad — Ejecutar múltiples réplicas
Cómo manejar más tráfico sin cambiar el código
Escalar significa correr más copias del mismo contenedor para atender más usuarios simultáneos. Docker Compose tiene soporte nativo para esto. Nginx distribuye las peticiones entre todas las réplicas automáticamente.
1
Escalar un servicio específico
# Correr 3 réplicas del MFE de transacciones
docker compose up -d --scale mfe-transactions=3

# Ver las 3 réplicas corriendo
docker compose ps
2
Actualizar Nginx para balancear carga entre réplicas
Cuando hay múltiples réplicas, Nginx necesita saber cómo distribuir:
# Agregar upstream en nginx.conf para balancear carga
http {
  upstream mfe_transactions {
    server mfe-transactions:3001;  ← Docker resuelve automáticamente
      entre todas las réplicas del servicio
  }

  server {
    listen 443 ssl;
    server_name mfe-tx.tudominio.com;

    location / {
      proxy_pass http://mfe_transactions;
      # ...resto de config igual
    }
  }
}
💡 Docker tiene un DNS interno que resuelve el nombre del servicio (mfe-transactions) a todas sus réplicas automáticamente. Nginx hace round-robin entre ellas sin configuración adicional.
